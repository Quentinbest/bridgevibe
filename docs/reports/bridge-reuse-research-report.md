# Open-source bridge reuse assessment

**Research snapshot: 17 October 2026 · Decision report before development**

## 1. Recommendation for review

**A conditional lesson-centered foundation exists, but no project was verified as a complete, dependable Web bridge game with a beginner curriculum and an accurate improvement coach.** The strongest starting point for a lesson-first product is [Bridge-Classroom](https://github.com/bridge-craftwork/Bridge-Classroom). The strongest inspected free-play feature reference is [Nickel Bridge](https://github.com/brannondorsey/nickel-bridge), whose original application-code license was not established. Neither is an unconditional adoption recommendation.

Two paths deserve a small validation exercise after this report is reviewed:

1. **Adapt Bridge-Classroom for a lesson-first product.** Reuse its authored lesson renderer, table/practice flow, accepted alternatives and progress architecture. Authored PBN answer evaluation runs locally; computed free-play grading calls BBA, whose reusable source/binary grant was not established. Disable those computed features for a local lesson subset or explicitly replace/clear the external grading, robot and solver dependencies. Correct the mastery denominator, verify asset/content rights and establish a teacher-reviewed curriculum. This path becomes more attractive when Vue and a Rust backend are acceptable and teacher/assignment workflows are useful. Its browser frontend does not establish autonomous browser-only operation for the full application.
2. **Assemble a smaller product from selected components.** Compare the MIT core of RalphLipe/ts-contractbridge for PBN/domain/scoring, Apache-licensed DDS for analysis, and rusty-bidding-bot versus deterministic Pons for a narrow authored bidding/explanation subset. Consider BEN as a replaceable robot backend and endplay for content authoring if those dependencies fit. Supply the authoritative game-state boundary, curriculum, rules explanations and coach evaluation as separate product work.

The reason for retaining both paths is concrete: Classroom already implements valuable teaching workflows, while a component approach avoids adopting its current service assumptions and teacher-oriented product model. Their relative effort cannot be responsibly estimated until the scope choices below are made. No implementation path, language, commercial model, multiplayer architecture or bidding system is selected by this report.

### What the evidence supports

- **Reuse for analysis is more mature than reuse for coaching.** DDS calculates perfect-information outcomes. It does not establish the quality of a decision made without seeing other hands.
- **Authored explanations are available.** Rusty, Pons, SAYC Bridge and Bridgit expose actual rules, meanings or constraints. Their coverage, conventions, fallback behavior and prose differ; none demonstrated improved learning in this investigation.
- **Licenses and test suites need file-level scrutiny.** GitHub's license detector missed valid grants in some projects. Other attractive public applications had no established original-code grant. Several libraries contain rules/scoring defects; some upstream tests explicitly preserve incorrect or incomplete behavior.
- **Browser UI, browser-compatible components and browser-only products are distinct.** Several projects with a Web interface require native/Python/.NET services. A WASM file does not prove mobile performance, deployment independence or hidden-hand safety.

These judgments derive from the pinned source and test evidence in the detailed profiles below. They are not popularity rankings or a claim that every promising project was found.

## 2. Method, scope and evidence standard

The investigation used independent searches for complete games, engines/analysis, teaching/coaching and rules/interchange, then followed dependencies and author links across those groups. Sources included two Web search systems; GitHub repository search, metadata, full recursive trees, commits/releases, actual license files, manifests, selected source/tests/workflows and CI records; SourceForge listings and reachable code trees; package indexes and author documentation. GitLab and Codeberg received explicit searches but yielded limited verifiable coverage.

Representative exact terms included:

- `open source contract bridge game web github tutorial AI coach`
- `github bridge card game javascript typescript scoring bidding library`
- `open source bridge AI BEN engine GitHub neural network`
- `contract bridge double dummy solver GitHub DDS endplay WebAssembly`
- `open source bridge bidding trainer tutorials SAYCBridge github`
- `"contract bridge" language:TypeScript`
- `"contract bridge" language:JavaScript`
- `bridge web multiplayer`, `bridge bidding in:name,description`, `bridge double dummy in:name,description`
- `site:gitlab.com "contract bridge"`, `site:codeberg.org "contract bridge"`
- `site:sourceforge.net/projects/ "bridge" "bidding"`
- `site:npmjs.com "bridge" "bidding"`, and PyPI-domain bidding searches.

The companion search-method file retains the exact query rounds, result limits and platform gaps. Broad “bridge” searches produced many blockchain, infrastructure and unrelated-game results. Those were excluded. Forks and moved repositories were deduplicated; source was followed to the canonical current owner where possible. A discovered repository was not treated as an inspected candidate merely because it appeared in search.

**Selection criteria:** relevance to the Web/teaching requirements; inspectable source and license; implemented functionality rather than planned features; rule and information correctness; explanation provenance; documentation/test substance; recent source maintenance; integration burden; and model/data/content rights. Stars were not used as proof of quality. Maintenance uses default-branch/source dates where established, not just `pushed_at` or a SourceForge page-update date.

**Evidence labels used throughout:**

| Label | Meaning | Limit |
|---|---|---|
| D | Documented by the project | A README or benchmark claim is not independently reproduced. |
| I | Relevant source, license, test or history inspected | Code inspection is not a successful build or end-to-end test. |
| T | Specific behavior executed in this investigation | Applies only to the stated fixtures/suite and revision. |
| CI | Successful upstream execution observed | Separate from our execution; adequacy of assertions remains a question. |

Some engine-source notes originally used “C” for code inspection and “I” for inference; the assembled report normalizes these to **I** and **judgment**, respectively.

**Stopping rationale:** searches covered complete applications, native games, rules/scoring, PBN/LIN/deal generation, deterministic and learned bidding, imperfect-information robots, double-dummy solvers, Web/WASM integration, curriculum and coaching. Targeted follow-ups uncovered the recent Bridge-Classroom/Rusty/BidBase ecosystem and materially changed the initial recommendation, so those were inspected before stopping. Subsequent value lay in testing the shortlist's actual constraints rather than indefinitely extending a noisy catalog.

**Remaining search/verification gaps:** GitHub queries were bounded first pages, not complete pagination; GitLab API/index coverage was limited; Codeberg access/indexing was blocked in places; non-English searching was limited; legacy SourceForge archives, CVS/SVN and source-in-JAR distributions were not comprehensively unpacked; forks and sibling services were not all audited. No common bot match, production browser/mobile run, complete multiplayer deployment, broad security/accessibility audit or learner study was performed. Initial execution/network limits were environment-specific; an authorized public clone later succeeded. These gaps prevent an exhaustive-coverage or production-readiness claim.

## 4. Behavior actually checked

The small checks were chosen to distinguish attractive interfaces and test claims from material implementation behavior. They do not establish full product readiness or bot strength.

| Project/check | Result actually obtained | Scope excluded |
|---|---|---|
| Bridge-Classroom existing Vitest selection | **125/125 passed**, nine files: PBN/play/rotation, card legality, authored lesson flow, dummy choices, lead timing and mocked Rusty orchestration | No production build/browser, real WASM or BBA/BEN/DDS, Rust API/mastery or multiplayer |
| SAYC Bridge core tests | **32/32 passed** | No Z3 bidder, 1,483-case baseline, server or memory test |
| DDS current Web JS suite | **288/288 passed** after exact missing fixtures were retrieved | Mocked interface tests; no current native/real WASM solver or Playwright |
| BEN candidate comparison tests | **15/15 passed** | Weighted candidate MP/IMP comparison only; not robot recommendations or full scoring |
| Older bridge-dds-js embedded WASM | **Two actual DD tables solved; 25 checked cells matched known fixtures** | Not current upstream DDS3, package rebuild, all API modes or browser performance |
| Three scoring functions: RalphLipe, bridge-tools, jfklorenz | **2,940 valid combinations agree**; **16 separately expected score examples passed** | Agreement is not an independent proof; no rubber/Chicago/tournament certification |
| RalphLipe bounded auction/PBN checks | Auction/declarer and selected invalid-auction rejection plus semantic PBN round-trip passed | No complete game-state authority |
| kduffie scoring probe | Three controls passed; **two made doubled/redoubled cases failed** | Isolated unchanged scoring methods, not a package build/full app |

The 2,940-score domain is 7 levels × 5 strains × 3 doubling states × 2 vulnerability states × 14 trick outcomes. Independent examples were checked against [WBF Law 77](https://www.worldbridge.org/wp-content/uploads/2017/03/2017LawsofDuplicateBridge-paginated.pdf). For example, nonvulnerable 2H doubled exactly should score 470; kduffie's method returned 110. That concrete failure outweighs a generic claim to implement bridge scoring.

Other executed boundary problems were a five-card final trick and invalid call values accepted by bridge-tools/core, an invalid 14-trick score accepted by RalphLipe, and a 300% top percentage for a one-board/four-result leaderboard in jfklorenz's explicitly unfinished function. These findings justify selecting components carefully and adding independent input/state validation.

Separate **inspected, unexecuted** defects include GNUBridge's incorrect score expectations, Bridgit's history-explanation stubs, Baker lesson/prose inconsistencies and Classroom's mastery denominator. Successful Nickel main-push CI at the exact inspected commit included unit/typecheck/build, Playwright and Docker steps; that upstream execution was observed, not rerun here. Later failed scheduled upkeep jobs were not confused with application-test failures.

## 5. Playing strength and teaching usefulness must be decided separately

A useful playing engine optimizes a game objective given an information set and partnership agreements. A useful coach additionally identifies the concept being learned, explains it correctly, accepts reasonable alternatives, distinguishes uncertainty from a mistake and chooses suitable practice. This is the product's central design requirement.

### Four questions every recommendation needs to answer

| Question | Required teaching behavior | Failure seen in the landscape |
|---|---|---|
| Is this action legal? | Authoritative state/rules check, independent of model output | Libraries that record plays without holdings validation |
| What does this bid mean in our system? | Versioned agreements and traceable constraints | “SAYC”/“2/1” labels with incomplete or unimplemented settings |
| Why is this choice sensible with what I knew? | Visible-information rationale, alternatives and uncertainty | Actual-deal DD result or model probability presented as correctness |
| What should I practice next? | Stable concept tags and validated progress/retention signals | Correctness/engine agreement or incomplete lesson coverage labeled mastery |

**Double-dummy review needs an explicit label.** It knows every hand and assumes optimal continuation. A line that works on the actual deal can be inferior when the unseen cards are uncertain. Sampling helps only if it uses information legitimately available to the player and a defensible distribution. Pons's inspected oracle holds both partnership hands fixed and shuffles opponents; that is useful contract study but is not the learner's information set during the auction. Nickel and BEN contain sampled-play designs, but no comprehensive leakage or sampling-quality audit was performed.

**Model probabilities are not correctness probabilities.** Nickel's grading compares its bidding policy's relative preference and adds selected SAYC allowances. Pons distinguishes authored priority from neural fallback percentages. These values may explain what an engine prefers; they do not prove a beginner's alternative was wrong.

**A bid meaning is not a decision rationale.** BEN's explain endpoints call BBA/EPBot; they can describe a convention without explaining why BEN's neural/sampled process selected it. Bridgit has real internal descriptions despite unfinished public history methods. Rusty has rule/unknown traces that could support honest explanation, but the application must preserve them. Selecting Pons's deterministic entry point also does not by itself prove that unused neural assets are excluded from a shipped binary; inspect the built artifact and its dependencies.

**Card-play teaching remains a separate gap.** No inspected reusable card-play coach was established as providing robust explanations based on the acting player's information. The strongest authored explanation components mainly concern bidding. Numerical play analysis and scripted card-choice lessons can support a coach, but recognizing concepts, comparing practical lines and explaining uncertainty still need independent teaching work.

**Unsupported cases must remain visible.** A missing rule, timeout or unavailable service must not silently become “Pass because your hand is too weak.” That precise risk exists in inspected small-coach and application-fallback paths. Use an explicit unsupported result, a safe scripted continuation or a separately identified fallback whose limits are clear.

For the initial product, favor a small, original or rights-cleared lesson set with teacher-approved decisions and accepted alternatives. Any language model used for conversation should verbalize verified rule/hand evidence, rather than independently decide legality, scoring or the correctness grade. Log which system, source rule, engine and information mode produced each explanation. These are recommended design criteria, not claims that a shortlisted project already implements all of them.

No common independent match benchmark or human learning study was run. Published BRL/Rusty/BEN/Pons metrics have different opponents, revisions, objectives, information assumptions and conventions. A numerical leaderboard would imply comparability that the evidence does not support.

## 6. Recommended reuse architecture and open choices

Treat the following as responsibilities to keep separable; it does not prescribe separate microservices or a final language.

| Responsibility | Candidate reuse | Work still owned by this product |
|---|---|---|
| Table and lesson experience | Bridge-Classroom if its workflow fits; Nickel only after license resolution | Mobile/accessibility review, novice pacing, rules reference, error recovery |
| Authoritative game state | Selected audited core functions/types; Classroom/Redouble/OpenSpiel as additional references | Card ownership, turn/legal-action boundary, dummy/claims/completion, untrusted input, replay |
| Scoring and interchange | RalphLipe core; audited alternative scorers; endplay/PbnTools offline | Variant, seat/strain/vulnerability mapping, score perspective, strict parser handling |
| Numerical analysis | DDS native/WASM; compare wrappers/ports only when necessary | Worker/service lifecycle, timeouts, device budget, result-mode labels |
| Bidding meanings | Rusty and deterministic Pons first; SAYC Bridge or Bridgit when system/backend fits | Explicit convention profile, supported subset, alternatives, novice prose |
| Playing robot | BEN backend or a separately validated policy | Information boundary, coherent partner system, reproducibility, errors/latency |
| Curriculum and coach | Classroom directives/history; rights-cleared Baker material or authored replacements | Truth/teaching review, progress definition, learning validation, uncertainty/abstention |

### Conditions that change the recommendation

| Open decision | Consequence |
|---|---|
| Lesson-first beginner launch | Classroom is the strongest foundation candidate; authored deterministic advice may be more valuable than maximum bot strength. |
| Free play before structured lessons | Nickel's feature fit improves, but its license gate remains. BEN service plus a new client becomes another candidate. |
| Browser-only/offline is required | Prioritize local authored lessons and rules/WASM workers. Classroom's authored lesson evaluator can be isolated; computed free-play BBA grading and HTTP analysis must be disabled or replaced. BEN and Python/.NET components are not direct browser runtimes. |
| Backend is acceptable | Native DDS, BEN, SAYC Bridge, Bridgit and endplay become practical options; serving, concurrency and system-isolation work remains. |
| SAYC vs 2/1 vs Acol/Precision/other systems | Re-evaluate the bidder and every lesson. A system label is insufficient: NT ranges, forcing status, conventions, competitive agreements and defensive carding must align. No equally deep Acol/Precision shortlist was established. |
| Duplicate vs rubber/Chicago/other variants | Most positive scoring evidence concerns duplicate contracts. Session state, rubber bonuses, vulnerability progression and tournament rules require separate coverage. |
| Live human multiplayer | Independently assess table/session authority, reconnection, redacted views, clocks, claims and cheating exposure. Nickel's asynchronous solo contests are not live four-human play; Classroom's table service was not separately cleared. |
| Advanced players later | Stronger sampling and alternative-line evaluation matter more; broaden systems and run controlled matches and expert review. Beginner teaching results do not establish advanced coaching. |
| Commercial/proprietary distribution | Resolve source, model, native-binary and content rights individually. Do not assume GPL forbids commercial activity or that an API boundary settles obligations. No-license and noncommercial artifacts may be disqualifying. |
| Small budget or team | Avoid new policy training, legacy desktop ports and several language stacks. Test one narrow lesson flow and one component alternative before estimating a product. |
| Existing Vue/Rust, TS, Python or .NET expertise | Changes integration cost substantially; it should break ties after rules/rights/teaching gates, rather than excuse their failure. |

## 7. Smallest practical validation before committing

These are **proposed next-phase experiments**, not work already completed and not an authorization to begin the product. Counts below are small decision-oriented starting points, not statistically sufficient proof or industry standards.

1. **Write a one-page experiment scope.** Choose one target beginner level, one scoring variant, one explicit bidding/convention profile, solo versus multiplayer, and whether a backend is acceptable. Leave the long-term roadmap open. Without this, “best engine” has no stable meaning.
2. **Clear the exact reuse bill of materials.** List only the files, packages, native engines, weights, card configurations, fonts/images and lesson text the experiment needs. Confirm their actual grants and notice requirements. Nickel stops here until original-code permission exists. For Classroom/Rusty/Pons/BEN, check the selected dependency path rather than the root label. If unresolved, test original lessons and deterministic components without the uncertain artifacts.
3. **Run a tiny legal-state/analysis integration.** Use roughly ten fixed deals plus the full finite contract-scoring domain. Cover dealer/declarer, pass-out, double/redouble, ownership, revoke attempts, dummy control, partial/final trick, duplicate cards and malformed input. Reproduce and close the defects relevant to the chosen path. Require deterministic accepted/rejected outcomes and no silent score fallback.
4. **Check the information boundary and failure handling.** For advice/robot modes restricted to the acting player's knowledge, hold visible hand/history constant, vary hidden layouts and replay with fixed randomness. Inspect requests/responses, not just chosen moves. Intentional all-hands lessons and DD review can depend on the full layout and must be identified as such. Check opening-lead visibility, opponent API views, service timeout and no-rule paths. Require no unauthorized hidden cards in these checks and explicit unsupported/fallback status; a finite check is not a proof of absence of all leakage.
5. **Compare explanation substrates on 20–30 teacher-reviewed decisions.** For bidding, use the same convention profile and authored expected meanings/acceptable alternatives for Rusty and deterministic Pons; substitute SAYC Bridge/Bridgit if that is the relevant system. Include a valid alternative bid, a forcing auction and an uncovered case. Also include card-play decisions about following suit, counting sure tricks and finesse uncertainty, including a misleading-DD example. Evaluate factual correctness, consistency with the engine's actual reason, readability, alternative handling and abstention separately from move strength.
6. **Demonstrate one lesson and one complete deal on a target phone/browser.** For Classroom, use the actual pinned WASM/service configuration, not mocked tests. For a component path, exercise one chosen solver and core. Measure cold load, responsiveness, peak memory and hard-deal latency. If using a backend, add a few concurrent/interleaved requests with different system settings. Decide acceptable limits from the intended audience and budget.
7. **Validate the improvement claim before committing to adaptive coaching.** Have a teacher review the first small curriculum and its progress formula. Then try a few novices on pre/post and delayed, unseen transfer examples; observe misconceptions and feedback clarity. This early pilot detects large teaching failures but does not substantiate a broad efficacy claim.

Stop a candidate's evaluation when a blocking license, rules or information-boundary defect has no acceptable small remedy. There is no need to run every project or broaden benchmarks merely to fill a comparison table.

### Decision requested at the end of this phase

Review the conditional paths and select the scope of the small validation exercise: **Classroom lesson foundation**, **component assembly**, or **neither until a named gap is resolved**. “No suitable foundation for the chosen constraints” remains a valid outcome. The current evidence justifies a shortlist and explicit gates, not a final technology selection.

## Detailed profiles: teaching, content and system bidders

### 1. Bridge-Classroom

**Snapshot:** main f97dab8cbd920f001fef9476e703a6cf14e759b7, default-branch commit **2026-10-15**. Repository created January 2026; not archived. Its recent activity is substantive but the project is young. [Commit](https://github.com/bridge-craftwork/Bridge-Classroom/commit/f97dab8cbd920f001fef9476e703a6cf14e759b7).

#### What is supported

The [lesson directive specification](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/documentation/lesson-directive-spec.md) defines authored instructions embedded in PBN: bidding prompts, explicit expected card choices, multiple valid cards, accepted alternative bids, hand visibility, current versus past trick display, backtracking and prose. This is backed by [pbnParser.js](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/src/utils/pbnParser.js) and [useDealPractice.js](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/src/composables/useDealPractice.js). In particular, makeBid compares the recorded auction call plus acceptedBids; makeCardChoice recognizes anyOf lists. Incorrect scripted choices advance using the expected card so subsequent lesson positions remain consistent. The application does not infer the lesson's truth from prose.

Tracking is more than a cumulative score. [CORRECTNESS_AND_MASTERY.md](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/documentation/CORRECTNESS_AND_MASTERY.md) distinguishes correct, corrected and failed attempts; spaced repeats; out-of-context practice; and derived lesson tiers. This is a useful architecture for a coach's practice history. It does **not** establish that the thresholds measure general bridge skill or that users learn better.

The [architecture document](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/documentation/app-architecture.md) explicitly separates authored guidance on fixed deals from computed comparison with an engine. It also contains future/proposed surfaces, so those tables should not be treated as a completed feature checklist. A separate untracked guided-practice mode is described as not built in that document.

#### Browser and backend boundary

[package.json](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/package.json) specifies Vue 3, Vite 5, Vue Router, an org convention-card package, Vitest and Playwright. Build prehooks fetch a pinned Rusty WASM release (v0.2.0 and SHA-256 are recorded in [rbb-wasm.release.json](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/scripts/rbb-wasm.release.json)). The actual browser WASM artifact was not exercised in this lane.

The [API Cargo.toml](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/bridge-classroom-api/Cargo.toml) and [API README](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/bridge-classroom-api/README.md) identify Rust/Axum/Tokio/sqlx/SQLite; identity, encrypted observations, assignments and teacher features require this backend. Multiplayer adds a separate bridge-table-service and optional live communication infrastructure; those services were not independently inspected here.

**Local does not mean independent of services.** [localEngine.js](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/src/composables/engines/localEngine.js) fixes the student's grading reference to BBA even when Rusty bids the other seats. [rustyBidder.js](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/src/composables/engines/rustyBidder.js) asks the WASM engine to stop when no rule applies, then takes BBA's call; on failed BBA lookup it supplies Pass. The fallback is logged but deliberately unflagged in the UI. For coaching, this needs explicit provenance and abstention/recovery behavior; otherwise a user may learn from an unavailable-engine fallback.

[cardplayBots.js](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/src/utils/cardplayBots.js) offers random, replay, rule-WASM and BEN-backed bots. BEN is HTTP. [ddsClient.js](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/src/utils/ddsClient.js) sends deals and play histories to a separate solver service. DDS is framed as a best-effort post-hand overlay. No local-browser benchmark or real network engine performance was established.

#### License, maintenance, docs and tests

The [root license](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/LICENSE) is the Unlicense. That software grant should be assessed separately from external BBA/BEN dependencies, lesson-content rights, fonts/assets and the independent convention-card package. There are extensive design and developer documents and many unit-test files. Default-branch [Frontend CI run](https://github.com/bridge-craftwork/Bridge-Classroom/actions/runs/38742162691) completed successfully at the inspected commit; its [workflow](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/.github/workflows/frontend-ci.yml) runs locked dependency install, tests, production build and site restructuring. **Actual local verification:** a public shallow clone at the pinned commit, npm ci with lifecycle scripts disabled, then nine existing Vitest files: PBN parser, play-section parser, parser rotation, card-play rules, lesson practice, dummy/card-choice handling, practice rotation, lead timing and mocked Rusty orchestration. **125 tests passed, nine files, 3.26 seconds.** This did not execute a production build, actual WASM bidder, backend, live browser UX, learning study or third-party engine call. The exact command and scope are recorded in TEST_EVIDENCE.md.

#### Material limitations and adaptation

A concrete progress-metric discrepancy exists: the mastery spec defines the denominator as all declared boards in a lesson, but [lesson_mastery.rs](https://github.com/bridge-craftwork/Bridge-Classroom/blob/f97dab8cbd920f001fef9476e703a6cf14e759b7/bridge-classroom-api/src/routes/lesson_mastery.rs) computes distinct boards ever encountered across users. A new installation can therefore label a lesson using an incomplete denominator; onboarding a fixed lesson catalog and verifying tier logic are necessary before presenting mastery claims.

For a lesson-first solo product, reuse the renderer, PBN model, table views and progress flow after checking assets/content licenses; replace environment-specific origins; prune or adapt identity/teacher features to the actual product; make fallback/reference differences visible; add beginner rules explanations and an educator-reviewed curriculum. For multiplayer, the separate table service becomes an additional candidate, not a feature licensed/tested merely by choosing this frontend. For a pure browser/offline product, isolate authored lessons and local rules and explicitly remove/replace network reference and solver dependencies. No high-level play-strength claim is warranted from this evidence.

### 3. Bridgit
